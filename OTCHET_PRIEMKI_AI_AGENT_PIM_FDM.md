# Отчёт о приёмке доработок AI-агента маппинга PIM+FDM

**Дата проверки:** 3 сентября 2026
**Объект:** REST API `/v1/mapping-tasks`, воркер заданий, дашборд `/agent` (проект Marketplace Sync, документация v6.0/v6.1)
**Окружение:** production-сервер fdm3mp.com, домен ecommpedia.ru, systemd-сервис `marketplace-bot`, Nginx + HTTPS
**Метод:** живые тесты API/БД/логов на сервере → пофайловое код-ревью (18 файлов) → функциональные E2E-тесты обоих типов задач → браузерная проверка дашборда

## 2. Найденные и устранённые дефекты

### Дефект 1 — не-ASCII Bearer-токен → HTTP 500 (п. 1.4, 1.5)
- **Файл:** `web/middleware/api_auth.py`
- **Причина:** `secrets.compare_digest()` бросает `TypeError` при двух не-ASCII `str` — необработанное исключение → 500. Подтверждено тестом до фикса.
- **Фикс:** сравнение в байтах (`encode("utf-8")`), constant-time сохранён.
- **Регресс:** тот же curl теперь возвращает **401**.

### Дефект 2 — неверный лимит для значений справочника канала (п. 1.1, 7.1)
- **Файлы:** `config/config.py`, `services/mapping/validators.py`
- **Причина:** переменная `AGENT_MAX_REFERENCE_CHANNEL_VALUES` (2000) была в `.env`, но отсутствовала в Config — валидатор проверял значения канала лимитом категории (1000). Валидный запрос FDM со справочником канала 1001–2000 значений получил бы ложный 422.
- **Фикс:** переменная добавлена в Config (+экспорт), валидатор использует её для каналов.
- Заодно дефолты Config выровнены с документацией v6.1: `AGENT_MAX_ATTRIBUTES` 300→**100**, `AGENT_MAX_CHANNELS` 3→**20**, `AGENT_MAX_CONCURRENT_JOBS` 2→**3**, `AGENT_POLL_INTERVAL_SEC` 2.0→**5.0**.

### Дефект 3 — критичное расхождение дефолтов с ТЗ (п. 1.1, 2.1)
- **Причина:** рабочий процесс до рестарта использовал `AGENT_MAX_CHANNELS=3` (дефолт старого Config), а спецификация FDM допускает до 4 каналов — 4-й канал был бы отвергнут с 422.
- **Фикс:** правка 2 (см. выше) + рестарт. Подтверждено логом старта: «MappingJobWorker запущен (параллельных заданий: 3, интервал опроса: 5.0 сек)» и проверкой Config: `CHANNELS: 20`.

### Дефект 4 — дублирование консольных логов вложенных логгеров (п. 8.3)
- **Файл:** `utils/logger_config.py`
- **Причина:** console-handler вешался на каждый модульный логгер + `propagate=True` → записи `web.routes.v1_api` печатались дважды (свой handler + handler родителя `web.routes`).
- **Фикс:** оба handler'а (консоль + файл) перенесены на корневой логгер, модульные — без handler'ов. Форматы записей, `AppLogger`, ротация — без изменений.
- **Регресс:** после POST — 1 строка лога (было 2). Бонус: WARNING от `Config.validate()` теперь попадают в journalctl.

## 3. Протокол интеграционного тестирования (п. 9)

### 3.2. E2E задача 1 — attribute_mapping
Payload: категория «Пылесосы» (5 атрибутов), 3 канала (Ozon, Wildberries, Яндекс.Маркет).
- `202` + jobId `0e7bf421c2e610c7bb2d88300519b3cb`; полный цикл за ~6 сек (dur 5.4)
- Связки 1–3 («Цвет», «Мощность», «Вес») — соответствия во всех 3 каналах с confidence 0.95–1.0
- Связка 4 («Тип аккумулятора») — только Ozon (частичное покрытие каналов — норма)
- Несопоставимый атрибут (mappingId 5) → `unresolved: [5]` — детерминированно
- Все `channelAttributeId` существуют во входных данных, каждый использован ≤1 раза на канал
- `infomodelAttributeId` подставлен из входных данных (LLM его не возвращает)
- БД: `matched_count=4, unresolved_count=1, duration_sec=5.4, category_name=Пылесосы`

### 3.3. E2E задача 2 — reference_value_mapping
Payload: атрибут «Цвет товара», 4 значения, 3 канала (у Яндекса пустой справочник).
- `202` + jobId `9a2e15830e192f6db710a0757f8a805f`; завершение за ~7 сек (dur 4.9)
- **Полнота:** ровно 12 записей (4 значения × 3 канала) — гарантирована кодом, не LLM
- Ozon: Чёрный→(1,"чёрный"), Белый→(2,"белый"), Серебристый→(3,"серебряный", синоним, 0.9), Графитовый→null
- WB: Чёрный→(11,"Черный"), Белый→(12,"Белый"), Графитовый→(13,"Графит", 0.9), Серебристый→null
- Яндекс (пустой справочник): все 4 → null
- Пары (channelValue, channelValueId) консистентны; строки каналов скопированы символ-в-символ
- БД: `matched_count=6, unresolved_count=6, attribute_name=Цвет товара`

### 3.4. Дашборд `/agent` (браузер)

## 4. Известные незначительные замечания (не блокируют, исправить при случае)

1. `services/mapping/reference_value_mapper.py` — мёртвый код: словарь `values_by_id` заполняется, но не используется.
2. `prompts/reference_value_mapping.txt` — опечатка «НЕ подиешь» (правильно: «НЕ подбирай»); на качество LLM не влияет.
3. `config/config.py` — дефолт `WEB_DOMAIN="galina-blanka.ru"` (старый домен); в production перекрыт `.env`.
4. Крайний случай воркера: остановка между `claim` и созданием Task оставляет задание в `processing` до следующего рестарта — самовосстанавливается через `recover_stale_mapping_jobs(0)` при старте.
5. `favicon.ico` — 404 (косметика, к агенту не относится).
6. nginx-лог фиксирует типичный скан-шум ботов (`/v1/.env`, `/v1/graphql` — 403/404); признак компрометации отсутствует, утечек нет.

## 5. Что осталось вне рамок

- **DELETE /v1/mapping-tasks/{jobId}** (п. 1.3) — отложен по согласованию; статус `cancelled` зарезервирован в БД и обрабатывается в GET-ответе.
- **Реальная интеграция с FDM** — передать команде FDM: base URL `https://ecommpedia.ru/v1`, токен `FDM_API_TOKEN` (у них — `FDM_AI_AGENT_API_KEY`), рекомендации: поллинг каждые 3 сек, бюджет 5 мин, лимиты payload (100/20/500/1000/2000).
- Unit-тесты (pytest) для validators/mappers — в Roadmap проекта.
